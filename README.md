# SuperMegaPlexCalc3000 (SMPC_3)

**SuperMegaPlexCalc3000** — предельно низкоуровневый, векторно-матричный DSL с прямым управлением регистрами, аппаратным синтаксисом и агрессивной системой диагностики. Создан для перемножения матриц на скорости кремния, работы со сложной булевой логикой и жесткого наказания за любые ошибки в архитектуре памяти.

Здесь нет сборщика мусора, виртуальных методов и дипломатичных предупреждений: либо код ложится в векторные регистры и исполняется за единицы тактов, либо рантайм с позором уничтожает процесс.

## Сборка

Нужен только clang. Ни cmake, ни make, ни внешних зависимостей.

```bash
./build.sh              # debug
./build.sh release      # -O3
./build.sh release test # собрать и прогнать всё
./build.sh clean
```

Скрипт сам находит clang в `C:\Program Files\LLVM\bin`, отслеживает зависимости от заголовков через depfile и собирает `src/kernels/` отдельно с `-mavx2 -mfma` — остальной код остаётся на базовом x86-64, потому что ветку выбирает CPUID, а не компилятор.

## Архитектурные принципы

* **Zero-Allocation Execution.** Никаких `malloc` в рантайме. Вся память выделяется едиными статическими аренами на старте, с обязательным выравниванием по 64 байтам. Размеры арен считает компилятор и записывает в заголовок модуля.
* **Direct Threading VM.** Байткод-машина на чистом C99 с таблицей переходов на прямых метках (`goto *dispatch_table[op]`). Таблица строится из того же X-макроса, что и перечисление опкодов, а её полнота проверяется на этапе компиляции.
* **Hardware-Aware Syntax.** Конструкция `[ПРЕФИКС] ТЕЛО [СУФФИКС]` передаёт управление регистрами, параллелизмом и алиасингом прямо в байт флагов каждой инструкции.
* **Zero-Diplomacy Diagnostics.** Система исключений не маскирует ошибки UB и не пытается их чинить. Любая попытка дёрнуть SIMD по невыровненному адресу или умножить несовместимые тензоры вызывает полный дамп регистров и бескомпромиссную критику квалификации автора.

## Спецификация формата

| Параметр | Значение |
| --- | --- |
| **Расширения файлов** | `.smpc` (исходный текст), `.s3b` (байткод) |
| **Magic Bytes** | `0x53 0x4D 0x50 0x33` (`SMP3`) |
| **Рантайм** | Чистый C99, Zero-Dependency, Direct Threaded Dispatch |
| **Память** | Flat Arena + 64-байтные дескрипторы тензоров |
| **Типы данных** | `f32`, `f64`, `i32`, `u64`, `raw_ptr`, веса `q8_0`, тензоры до 4D |
| **Инструкция** | Ровно 8 байт, декодируется без ветвлений |

## Пример кода

```smpc
// Инициализация матриц в выровненной арене
[#arena:0]  *&A<f32:1024,1024>  ->  @alloc  =>  $r1;
[#arena:0]  *&B<f32:1024,1024>  ->  @alloc  =>  $r2;

// Параллельный GEMM с запретом алиасинга указателей
[#simd:v256]  $r1 -> @mmul($r2) => *&C<f32:1024,1024>  [!no-alias, ?strict];

// Выборка строки, активация и редукция в скаляр
[^raw]  *&C[0, ..] -> @relu -> @reduce.add => $f0  [~flush-to-zero];
```

Во что это превращается:

```
; строка 6
0006  [v256,str,na       ] loadt    r3, T2 C<f32:1024,1024> a0:0x800000
0007  [v256,str,na       ] mmul     r3, r0, r1
; строка 9
0008  [v256,ftz,raw      ] loadt    r3, T3 C<f32:1024> a0:0x800000
0009  [v256,ftz,raw      ] loadt    r4, T4 %t4<f32:1024> a0:0xC00000
0010  [v256,ftz,raw,fuse ] relu     r4, r3
0011  [v256,ftz,raw      ] redadd   r5, r4
```

Срез `*&C[0, ..]` — отдельный дескриптор с тем же базовым адресом: копии нет, только другая форма и шаг. Результат `@mmul` пишется прямо в буфер `C`, без промежуточной копии, — но только потому, что `C` не читается этой же инструкцией.

Флаг `fuse` на `relu` означает, что его результат не попадёт в память вообще: `redadd` заберёт значения прямо из регистров. Компилятор ставит этот флаг, когда промежуточный буфер читает ровно одна следующая инструкция, — сам рантайм этого знать не может.

## Система исключений в действии

```text
[FATAL SKILL ISSUE :: E0419] in kernel.smpc:8:22
  8 | [#simd:v512]  $r1 -> @mmul($r2) => *&C<f32:1024,512>  [!no-alias];
    |                      ^~~~~~~~~~
    |-- ОШИБКА: Размерности K не сходятся при матричном умножении.
    |-- ДЕТАЛИ: Левый множитель f32:1024,1024, правый f32:512,512.
    |           Размерности K не сходятся (1024 != 512).
    |-- ДИАГНОЗ: Твои руки не приспособлены для линейной алгебры.
    +-- ИСПРАВЛЕНИЕ: Вызови @transpose над правым множителем (получится
    |                [512,512]) или перепиши свой код на Scratch.
```

Диагноз берётся из пула своей категории — их семь, на 71 строку. Выбор детерминированный, по хешу `(код, строка, колонка)`: одна и та же ошибка всегда даёт одно и то же оскорбление. Это нужно для снимков вывода и заодно перестаёт выглядеть как рулетка.

Пул говорит про категорию, а не про конкретную беду, и там, где это мажет мимо, код несёт **собственный** диагноз — он перебивает пул. Разница видна сразу: `E0419` про несходящиеся `K` всегда получает строку про линейную алгебру, а не случайную из памяти. Тонкость в том, что промахнувшийся диагноз — не просто вялая шутка: строка «Точка с запятой существует» на ошибке о скобках отправит человека искать не то. Поэтому в пулах живут формулировки, верные для всей категории, а привязанные к одному коду вынесены в реестр рядом с его `ОШИБКА` и `ИСПРАВЛЕНИЕ`.

Опечатки ловятся расстоянием Левенштейна с порогом от длины имени: `@realu` → `@relu`, `~flush-to-zerro` → `~flush-to-zero`, `*&Alpah` → `*&Alpha`. На непохожем слове подсказка не выдумывается.

## Устройство

```
include/smpc3/     публичные заголовки
src/core/          арена, диагностика, CPUID, типы, ввод-вывод
src/front/         лексер, парсер, AST, семантика
src/back/          эмиттер байткода, контейнер .s3b, дизассемблер
src/vm/            машина прямой диспетчеризации, пул инстансов, вывод
src/kernels/       скалярный эталон, AVX2+FMA, диспетчер по CPUID
src/plat/          всё, что просится у ОС: страницы, потоки, часы, консоль
tests/             тесты по фазам + снимки вывода
examples/          рабочие примеры и намеренно сломанные
```

Проход выглядит так:

```
.smpc → лексер → парсер → семантика → эмиттер → .s3b → VM → ядра
         токены   AST      символы,     байткод         регистры  скаляр
                           арены,                                 или
                           формы                                  avx2+fma
```

### Ключевые решения

**Об ОС знает один файл.** Страницы под арены, потоки, часы, переменные окружения и консоль собраны в `include/smpc3/plat.h`; реализация для Windows и POSIX — `src/plat/host.c`. Компилятор, VM и ядра зовут только её, поэтому те же исходники собираются и в ядро операционной системы, где нет ни `malloc`, ни потоков ОС, ни файлов, — со своей реализацией этого интерфейса. Весь путь от текста до модуля — одна функция `smp_compile` (`include/smpc3/compile.h`): ею пользуется и CLI, и тот, у кого программа приходит не из файла.

**Скобочные группы различимы по одному токену вперёд.** `[` + `#`/`^` — префикс, `[` + `!`/`?`/`~` — суффикс, `[` + число/`..`/`$` — индекс. Грамматика получается LL(2) без возвратов.

**Оси и шаги — `uint32_t`, шаг в элементах, а не в байтах.** Ось вмещает словарь языковой модели (у Qwen2.5 — 151 936 токенов), а число элементов тензора ограничено тем же `uint32_t`, так что шаг любой оси в него тоже влезает. Смещение в арене — `uint64_t`: арена не упирается в 4 ГиБ. Дескриптор — 64 байта, ровно строка кэша.

**Broadcast отсутствует намеренно.** Формы либо совпадают, либо это ошибка.

**Номер арены живёт в трёх старших битах `flags` дескриптора.** Отдельного поля нет: восемь арен ровно укладываются в биты 13..15, которые иначе простаивали бы.

**Поэлементные стадии сливаются в один проход.** `@add -> @relu -> @scale` читает вход один раз и один раз пишет результат, вместо прохода по памяти на каждую стадию. Свёртка тоже закрывает цепочку: у `@relu -> @reduce.add` промежуточного буфера нет вовсе.

Пока данные держатся в L3, лишние проходы почти бесплатны, и первый замер это скрыл. За пределами L3 каждая стадия честно платит DRAM:

```
тензоры по 16 МиБ (рабочий набор 48 МиБ, L3 = 24 МиБ)
  @add -> @relu -> @scale     8125 -> 2750 мкс    2.95x
  @abs -> @reduce.add         2625 ->  625 мкс    4.2x
```

Слияние живёт в одном бите флагов инструкции (`SMP_IF_FUSE`) — ни нового опкода, ни секции, ни лишнего байта в файле. Рантайм, который этот бит игнорирует, исполнит модуль правильно, просто медленнее.

**Цепочку начинает и `@mmul`.** У блочного GEMM уже есть проход по результату — цикл выгрузки тайла, — и эпилог укладывается прямо в него: `@mmul -> @relu -> @add` не заводит промежуточного буфера. Применяется он только на последнем k-блоке, потому что до него в `C` идёт накопление и `relu` над незаконченной суммой срезал бы промежуточный шаг.

Стадии при этом идут отдельными проходами по строке панели, а не все сразу на каждый элемент. Так можно: они поэлементные и независимые. Первая версия разбирала стадию на каждые восемь чисел, и в тайле шириной 16 этот разбор стоил дороже самой арифметики — слияние съедало собственный выигрыш (2375 мкс против 2250 у отдельного прохода). Строка панели лежит в L1, так что лишние проходы по ней бесплатны, а проход стал длиннее разбора:

```
M=N=2048, K=64 (C и D по 16 МиБ, рабочий набор 32 МиБ > L3)
  @mmul -> @relu -> @scale    2125 -> 1250 мкс на вызов
```

Ниже L3 выигрыша нет вовсе: на квадратном `N=1024` разница между слитым и раздельным эпилогом не выходит за шум (±1.5%). Это ровно то же правило, что и для поэлементных цепочек, — платит DRAM, а не арифметика.

**`v512` без железа** → `W0512` и двойной проход по `v256`; с `?strict` → фатальный `E0502`. Ширину, которую видит компилятор, можно подменить через `SMPC3_VEC_BITS=128|256|512` — чтобы воспроизвести чужой отчёт об ошибке, не имея того же процессора.

## Развёртка

Ветвлений в языке нет и не будет. А повторить одну инструкцию N раз, подставляя на каждом повторе его номер, — можно:

```smpc
[#arena:0]  *&M<f32:8,8> -> @alloc => *&M;

// строка k заполняется числом k
[#repeat:8, #index:i]  *&M[$i, ..] -> @fill($i) => *&M[$i, ..];

// сумма строки k ложится в k-й элемент результата
[#arena:0]  *&R<f32:8> -> @alloc => *&R;
[#repeat:8, #index:i]  *&M[$i, ..] -> @reduce.add => *&R[$i];
```

Имя из `#index` заменяется литералом везде, где встретится, — и в квадратных скобках, и в позиции обычного операнда. Поэтому `@fill($i)` получает константу, как ему и положено: аргумент `@fill` едет в пул констант, регистр там оказаться не может.

**Это развёртка, а не цикл.** Тело дублируется на этапе компиляции, обратного перехода не возникает, и обещание «инструкция декодируется без ветвлений» остаётся в силе. Платится за это размером модуля: он растёт ровно в N раз, и потолок в 4096 повторов — прямое следствие, а не круглое число.

Взамен индекс известен компилятору, и это меняет не только скорость:

```
0009  [v256] loadt r2, T2 M<f32:8> a0:0x0     ; повтор 0
0014  [v256] loadt r2, T4 M<f32:8> a0:0x20    ; повтор 1
0019  [v256] loadt r2, T6 M<f32:8> a0:0x40    ; повтор 2
```

Смещения посчитаны на компиляции — инструкции `sliced` не появляется вовсе, а с ней исчезают и её рантайм-проверки. Выход за границу оси становится обычной диагностикой:

```text
[FATAL SKILL ISSUE :: E0410] in bad.smpc:2:27
  2 | [#repeat:6, #index:i] *&M[$i, ..] -> @abs => *&M[$i, ..];
    |                           ^~
    |-- ОШИБКА: Индекс за пределами тензора.
    |-- ДЕТАЛИ: Ось #0 имеет размер 4, а запрошен элемент 4.
    |           Это повтор #4 из 6: развёртка [#repeat] в 2:2.
    +-- ИСПРАВЛЕНИЕ: Сверь индекс с формой. Границы массива -- не рекомендация.
```

Сообщение здесь одно, хотя за границу ушли два повтора из шести. Правило «не больше одной претензии на инструкцию» считает по написанному, а не по порождённому: иначе опечатка внутри `[#repeat:1024]` отчиталась бы тысячей одинаковых сообщений об одной строке. Номер повтора при этом назван — без него непонятно, откуда взялась четвёрка, ведь в исходнике её нет.

Слиянию развёртка не мешает: внутри каждой копии цепочка сливается как обычно.

Объявить тензор внутри развёртки нельзя — N копий объявили бы одно имя N раз, и вместо N сообщений о повторном объявлении компилятор говорит это прямо (`E0310`).

## Обмен с внешним миром

До появления `@load` и `@store` данные попадали в программу только литералами, а наружу уходили только печатью. Этого хватало примерам и не хватало ничему больше: посчитать чужой массив язык не мог.

```smpc
[#arena:0]  *&A<f32:1024> -> @load  => *&A;
[#arena:0]  *&C<f32:1024> -> @alloc => *&C;

[#simd:v256]  *&A -> @relu -> @scale(2.0) => *&C  [!no-alias];

*&C -> @store => $put;      // сколько байт записано
```

```bash
smpc3 run prog.smpc --in A=a.bin --out C=c.bin
```

С другой стороны это обычный сырой массив — `array.tofile` и `numpy.tofile` пишут ровно то, что нужно:

```python
array.array('f', values).tofile(open('a.bin', 'wb'))
```

**Имени файла в исходнике нет.** Программа знает имя *тензора*, путь приезжает из командной строки. Иначе путь пришлось бы писать в `.smpc`, а строкового типа в языке нет — заводить его ради имени файла было бы нечестно. Побочная выгода: одна и та же программа считает разные данные без пересборки.

**Заголовка у файла нет.** Объявление тензора в исходнике и есть схема; заголовок дублировал бы её и однажды с ней разошёлся. Проверяется размер — байт в байт:

```text
|-- ОШИБКА: Привязанный файл не сошёлся с тензором.
|-- ДЕТАЛИ: Файл 'a.bin' занимает 64 байт, а тензор f32:9 просит 36.
```

Тип элемента остаётся на совести автора: `f32:8` и `f64:4` занимают одинаковые 32 байта, и различить их по содержимому нечем. Это такое же обещание, как `[!no-alias]`.

**`@store` — свёртка, как `@emit`.** Съедает тензор, отдаёт число записанных байт. Отдельной «процедуры без результата» в языке нет и не понадобилось.

**Обещание про отсутствие `malloc` не нарушено.** Файл читается прямо в арену: место под тензор компилятор посчитал заранее, рантайм лишь заполняет его байтами.

Оба обязаны стоять первой стадией и работать с плотным тензором. Причина одна: привязка идёт по имени, а после любой считающей стадии остаётся безымянный временный буфер, и записывать срез с шагом пришлось бы по кускам. Оба случая ловятся на сборке — иначе человек увидел бы в рантайме внутреннее имя `%t1` вместо объяснения.

Пул и `--out` вместе не работают: `N` инстансов писали бы в один путь наперегонки, и содержимое зависело бы от того, кто закончил последним. `--in` при этом разрешён — читать один файл могут все.

### Хранилище вместо файлов

Там, где файлов нет вовсе, — в ядре NablaOS, — у VM есть второй обмен: хранилище (`SmpStore` в `vm.h`). Хозяин подключает его вызовом `smp_vm_store`, и `@load`/`@store` работают с объектом того же имени, что тензор, без привязок и путей. Объект переживает программу: одна кладёт, другая через минуту достаёт.

```smpc
[#arena:0]  *&V<f32:16> -> @fill(1.5) => *&V;
*&V -> @store => $put;             // первая программа

[#arena:0]  *&V<f32:16> -> @load => *&V;
*&V -> @reduce.add => $s;          // вторая: $s = 24
```

Объект хранилища, в отличие от файла, помнит тип и форму, и `@load` сверяет их, а не один размер: `f32:16`, `f64:8` и `f32:4,4` занимают по 64 байта, но подсунуть одно вместо другого нельзя.

```text
|-- ОШИБКА: Объект в хранилище не сошёлся с тензором.
|-- ДЕТАЛИ: В хранилище лежит V<f32:16>, а объявлен V<f64:8>.
```

Своих кодов у хранилища три: `E0608` — объекта нет, `E0609` — тип или форма не те, `E0610` — положить некуда.

## Пул инстансов

Один скомпилированный модуль, N независимых инстансов. У каждого свои арены,
свой регистровый файл, своя рабочая память ядер и свой журнал диагностики.
Общего между ними — только сам модуль, а он неизменяем.

Именно поэтому инстансы раскидываются по потокам **без единого мьютекса**:
разделяемого изменяемого состояния просто нет. Единственная синхронизация во
всём пуле — атомарный счётчик выданных заданий.

```bash
smpc3 run examples/pool.smpc -n 128 -j 16
```

```
инстансов : 128 на 16 потоках
инструкций: 4992
время     : 0.0021 c
темп      : 61273.3 инстансов/с
```

`@fill.instance` — единственное, чем инстансы отличаются друг от друга изнутри
языка. Без него N копий посчитали бы N раз одно и то же.

Аллокации происходят при подъёме пула и только там: на исполнении ни один
инстанс не берёт ни байта.

Журнал инстанса живёт в памяти, а не в файле. Это не мелочь: пока журналом был
`tmpfile()`, каждый инстанс держал открытый дескриптор, и пул упирался в лимит
CRT — 512 файлов минус `stdin`/`stdout`/`stderr`. Заявленные 1024 инстанса были
недостижимы, пул не поднимался уже с 510, а отказ выглядел как `пул не
поднялся`, без кода и без объяснения. Теперь потолок достижим:

```bash
smpc3 run examples/pool.smpc -n 1024 -j 16
```

Буфер журнала конечен — 16 КиБ на инстанс. Если вывод в него не влез, отчёт
говорит об этом прямо: половина диагностики, выданная за целое, хуже, чем
честное «обрезано».

### Чего это стоило

Многопоточность вскрыла то, что до неё было безобидным: **буферы упаковки GEMM
лежали в глобальных массивах**. Два инстанса в разных потоках затирали панели
друг друга — без падения, без диагностики, просто неверные числа у части
инстансов. Рабочая память стала принадлежать инстансу.

Тест на это проверен от обратного: с общим буфером **31 инстанс из 32** даёт
расхождение, тысячами испорченных элементов.

Там же нашлась гонка помельче — общий статический буфер форматирования
диагностики рантайма.

### Один GEMM на все ядра

Пул раскидывает по потокам независимые программы. Одной программе с одним большим умножением это не помогает — а именно так выглядит прямой проход модели. Поэтому крупный `@mmul` делится сам: C режется на плитки — по строкам блоком MC, по столбцам так, чтобы плиток было хотя бы вдвое больше потоков, — и плитки раздаются потокам через атомарный счётчик. У каждого потока свой комплект панелей в рабочей памяти VM: общий комплект на двоих — та самая гонка, из-за которой рабочая память и перестала быть глобальной.

**Результат бит в бит тот же, что у одного потока.** Плитка считается тем же блочным циклом с тем же разбиением по K, так что порядок сложения у каждого элемента не меняется. Тест сравнивает точно, а не с допуском, — и проверен от обратного: сдвиг эпилога на угол плитки или потерянный на исполнителях FTZ ловятся сразу.

При `M = 1` — вектор на матрицу, шаг генерации токена — делятся одни столбцы. Мелкие умножения (`M·N·K < 2²²`) не делятся: раздача дороже арифметики. Инстансы пула поднимаются с одним комплектом — они и так параллельны.

## Производительность

```
GEMM f32 на одном ядре, ГФЛОПС (i7-13620H, поток закреплён за P-ядром)
     N      скаляр    avx2+fma   ускорение
  ----   ---------   ---------   ---------
    64      16.1        70.9        4.4x
   128      16.9        88.3        5.2x
   256      16.8       108.2        6.4x
   512      16.8       112.7        6.7x
  1024      15.6       103.4        6.6x
```

**Почему «скаляр» не 1 ГФЛОПС.** Раньше в этой колонке стояло около единицы, а
ускорение выходило стократным — но сравнение было нечестным. Эталон разбирал
тип элемента на каждом обращении и звал операцию через указатель на функцию;
через косвенный вызов компилятор цикла не видит и не векторизует его. Мерилось
не «скаляр против SIMD», а «медленный обход против SIMD».

Теперь тип разбирается один раз до цикла, и clang сам векторизует эталон
(`src/kernels` собирается с `-mavx2 -mfma` целиком). Колонка «скаляр» — это
автовекторизация, а `avx2+fma` — ручное блочное микроядро с упаковкой панелей.
Четыре-семь раз и есть цена, которую платят за то, что компилятор так не умеет.

Побочный выигрыш куда больше стократного: раз скалярная ветка обслуживает всё,
что не `f32` с плотной раскладкой, ускорились `f64`, `i32`, `u64` и любые срезы
с шагом — `f64` GEMM пошёл с 1.5 до 33.5 ГФЛОПС.

**О достоверности этих чисел.** На гибридном процессоре поток закрепляется за
ядром один раз и сидит там весь прогон: попал на E-ядро — и AVX2 идёт впятеро
медленнее, причём стабильно, так что повторные проходы этого не сглаживают.
Поэтому `smpc3 bench` прибивает поток к P-ядру, и не к нулевому: Windows вешает
на логический процессор 0 прерывания, и он даёт вдвое меньше остальных
(93 против 127 ГФЛОПС на N=256).

Даже с закреплением разброс между прогонами на нагруженной или прогретой машине
доходит до двух раз. Числа выше — порядок величины, а не паспортные данные.

Пик ~113 ГФЛОПС — около трёх четвертей теоретического потолка одного ядра. Микроядро 6×16: двенадцать накопителей `ymm`, два регистра под `B`, один под широковещание `A` — пятнадцать из шестнадцати. Упаковываются оба операнда; блокировка `MC=96`, `KC=256`, `NC=256` держит обе панели в L2.

**Эти числа не подбираются на лету.** Развёртка по соседним точкам даёт в лучшем случае 2–3%, а разброс между прогонами одной и той же сборки доходит до 13% — подбирать тоньше нечем. «Больше» тут вдобавок не значит «лучше»: `MC=384` роняет N=1024 со 117 до 85 ГФЛОПС, `KC=512` роняет N=512 со 119 до 88.

Что рантайм действительно делает — проверяет, влезает ли выбранное в **этот** L2. Умолчания просят 352 КиБ и молча предполагают кэш не меньше полумегабайта; на ядре с 256 КиБ (Skylake, Zen 2) панели начинают вытеснять друг друга, и получается ровно тот обвал вдвое, что виден в развёртке. Размеры кэшей читаются через CPUID, и блокировка ужимается — только если не влезает:

```
L2 неизвестен  ->  96/256/256, панели 352 КиБ
L2 =  256 КиБ  ->  96/136/256, панели 187 КиБ
L2 >= 512 КиБ  ->  96/256/256, без изменений
```

`smpc3 info` показывает и размеры кэшей, и выбранные блоки. Подменить расчёт руками можно через `SMPC3_GEMM_BLOCK=MC,KC,NC` — ровно так же, как `SMPC3_VEC_BITS` подменяет ширину вектора, и ровно за тем же: воспроизвести чужой замер, не имея того же процессора.

Буферы упаковки принадлежат инстансу VM и выделяются один раз при подъёме:
обещание про отсутствие `malloc` на исполнении не нарушено, а глобального
состояния, из-за которого ядро было непригодно для потоков, больше нет.

## Примеры

| Файл | О чём |
| --- | --- |
| `hello.smpc` | коды ASCII в тензоре — Hello World без вывода вообще |
| `hello2.smpc` | тот же текст, но **вычисленный**: шифр Цезаря снимается одним векторным сложением |
| `calc.smpc` | калькулятор: числа по конвейеру, литералы таблиц, `@div` и `@sqrt` |
| `bad_calc.smpc` | ошибки калькулятора — `SMPC3_DIAG=compact` показывает их коротко |
| `table.smpc` | таблица умножения одним `@mmul`, напечатанная построчно |
| `bars.smpc` | столбчатая диаграмма, где форма баров получена из `relu`, а сетка — из внешнего произведения |
| `dotprod.smpc` | скалярное произведение, нормы, расстояния через `@mul` + `@reduce` |
| `slices.smpc` | строки, столбцы, шаги, транспозиция, запись в срез |
| `types.smpc` | все пять типов, приведения, потеря точности, насыщение |
| `gemm.smpc` | арифметика, проверяемая вручную |
| `forward.smpc` | прямой проход двухслойной сети |
| `pool.smpc` | пул инстансов: `@fill.instance` и независимые арены |
| `repeat.smpc` | развёртка `[#repeat:N]`: индекс как срез и как значение |
| `io.smpc` | `@load` и `@store`: тензор из файла и обратно |
| `rank.smpc` | кусочно-линейное ранжирование без единого ветвления |
| `kernel.smpc` | пример из спецификации дословно |
| `broken.smpc` | лексические ошибки |
| `bad_syntax.smpc` | синтаксические ошибки и восстановление |
| `bad_sema.smpc` | семантические ошибки, включая `E0419` |
| `bad_repeat.smpc` | развёртка, заданная неверно |
| `trap.smpc` | ловушка рантайма под `?strict` |

```bash
smpc3 run examples/hello.smpc
```

Строкового типа в языке нет и не появилось. Вывод устроен как ещё одна
свёртка: `@emit.*` съедает тензор и отдаёт скаляр — число выведенных
элементов. Форматов шесть, и они различаются точечным суффиксом ровно так же,
как `@reduce.add` и `@cast.f32`:

| | |
| --- | --- |
| `@emit.text` | кодовые точки как UTF-8, без разделителей |
| `@emit.line` | то же плюс перевод строки |
| `@emit.dec` `@emit.hex` `@emit.bits` | целые в своей системе счисления |
| `@emit.num` | вещественные |

**Ни одной новой конструкции грамматики.** Формат едет в поле `aux`
инструкции — том же, где у арифметики лежит тип константы, — так что байткод
не вырос ни на байт. Аллокаций нет: буфер вывода фиксированный, на стеке.

Текстовые форматы печатают коды, а коды — целые, поэтому приведение обязано
быть явным:

```smpc
*&T -> @cast.i32 => *&Ti<i32:9,9>;   // молча округлять язык не станет
*&Ti[0, ..] -> @emit.dec => $n;
```

И вот тут язык перестаёт быть калькулятором без дисплея. `bars.smpc` рисует
диаграмму, не записав руками ни одного символа: ветвлений в языке нет, но
ступенька собирается из `relu`, а сетка — из двух внешних произведений.

```
    relu(x) - relu(x - 1)  =  0 при x <= 0,  1 при x >= 1
```

## Проверки

```bash
./build.sh release test
```

- **2736 юнит-тестов** по фазам: арена и типы, лексер, парсер, семантика, эмиттер и контейнер, VM, ядра.
- **35 снимков вывода** (`tests/golden.sh`) — сравнение диагностики посимвольно. Ловят то, чего не видят тесты на структурах: уехавшую каретку, потерянную подсказку, изменившуюся формулировку.
- **Численная сверка** векторных ядер со скалярным эталоном. Поэлементные операции обязаны совпадать точно; свёртки — с допуском, потому что порядок сложения другой. GEMM проверяется на 20 конфигурациях, включая все комбинации хвостов по M, N и K.
- **AddressSanitizer** — весь набор проходит чисто.

Чтобы обновить снимки после осознанной правки формулировок:

```bash
./tests/golden.sh --update
```
